# Migration Notes — esp-claw → esp-claw (new) / edge_agent

Board: Waveshare ESP32-S3-Touch-AMOLED-1.75
Old project: `C:\esp\projects\esp-claw\application\esp32-s3-touch-assist`
New project: `C:\esp\projects\esp-claw-new\application\edge_agent`

## Why migrate

The old repo predated the `boards/<vendor>/<board>/` convention. The board lived
directly under `components/waveshare_esp32_s3_touch_amoled_175/`, which required:

- A manual patch step after every `idf.py bmgr`-equivalent regen, editing
  `components/gen_bmgr_codes/CMakeLists.txt` by hand to add
  `REQUIRES espressif__esp_lcd_co5300 waveshare__esp_lcd_touch_cst9217`.
- A non-functional `sdkconfig.defaults.board` — confirmed via direct testing
  that this file was never actually wired into the build's `SDKCONFIG_DEFAULTS`
  chain. Any flags placed there silently did nothing.
- A separate, manually-discovered fix: adding
  `set(SDKCONFIG_DEFAULTS "sdkconfig.defaults;components/gen_bmgr_codes/board_manager.defaults")`
  to the top-level `CMakeLists.txt`, which DID work, because
  `board_manager.defaults` (auto-generated by the regen script) correctly
  mirrors `sdkconfig.defaults.board`'s content — it was just never loaded.

The new repo uses `esp-bmgr-assist` (`pip install esp-bmgr-assist`) and
`idf.py bmgr -c ./boards -b <board_name>`, which auto-generates both
`components/gen_bmgr_codes/CMakeLists.txt` and `idf_component.yml` correctly,
with no manual patch step required.

## What was ported

Copied directly from the old board folder into
`boards/waveshare/waveshare_esp32_s3_touch_amoled_175/`:

- `board_devices.yaml`
- `board_peripherals.yaml`
- `board_info.yaml`
- `setup_device.c`
- `setup_device.h`
- `README.md`

Deliberately NOT ported:

- `board_dummy.c` — believed to be a stub file needed only because the old
  board lived under `components/` and needed to satisfy
  `idf_component_register()`'s requirement for a source file under the old
  patch-based workflow. Not needed under the new `boards/` convention, which
  has no per-board `CMakeLists.txt` at all (confirmed against the
  `waveshare_ESP32_S3_RLCD_4_2` reference board).
- Old `sdkconfig.defaults.board`'s three `CONFIG_ESP_BOARD_PERIPH_GPIO_SUPPORT`,
  `..._I2C_SUPPORT`, `..._I2S_SUPPORT` flags. RLCD's own
  `sdkconfig.defaults.board` has none of these and builds clean, confirming
  the new generator handles peripheral support flags automatically/correctly
  (this was the core regression in old repo's 0.5.14 bump that consumed an
  entire prior session to diagnose and patch around).
- The `SDKCONFIG_DEFAULTS` CMakeLists.txt line from the old project. Tested
  directly: new repo's top-level `CMakeLists.txt` also lacks this line, but
  building `waveshare_ESP32_S3_RLCD_4_2` succeeded with zero modification.
  The underlying regression this line fixed in the old repo does not appear
  to be present in the new repo's generator.

## Required new addition (not a carry-over, a real fix)

`board_devices.yaml`'s `display_lcd` device had a dependency line that was
commented out, with a note: *"If an upstream CO5300 component becomes
available, pin it here. Until then setup_device.c drives the raw init
sequence."* This component is now available. Uncommented:

```yaml
    dependencies:
      espressif/esp_lcd_co5300: ">=1.0.0"
```

This is a genuinely supported, regen-safe YAML field (confirmed: the touch
device's analogous `waveshare/esp_lcd_touch_cst9217` dependency was already
present and uncommented, and it correctly flows through to the generated
`idf_component.yml`). No CMake patching needed — this was the actual fix,
not a workaround.

Process for finding this: attempted adding the dependency directly to the
generated `components/gen_bmgr_codes/idf_component.yml` — confirmed this file
is fully overwritten on every `idf.py bmgr` run and does not merge board-level
overrides. Also attempted creating a board-folder-level `idf_component.yml` —
also not picked up. The correct, surviving mechanism is the `dependencies:`
field inside `board_devices.yaml` itself, per-device.

## `sdkconfig.defaults.board` — new trimmed version

Old file carried three workaround flags no longer believed necessary, and a
generic `partitions.csv` reference. New repo ships per-flash-size partition
CSVs (`partitions_8MB.csv` / `_16MB` / `_32MB`).

```
# sdkconfig.defaults.board
# Waveshare ESP32-S3-TOUCH-AMOLED-1.75
# Confirmed from schematic and hardware specifications.

# ── Flash (16 MB, QIO at 80 MHz) ──────────────────────────────────────────
CONFIG_ESPTOOLPY_FLASHSIZE_16MB=y
CONFIG_ESPTOOLPY_FLASHMODE_QIO=y
CONFIG_ESPTOOLPY_FLASHFREQ_80M=y

# ── PSRAM (8 MB Octal at 80 MHz) ──────────────────────────────────────────
CONFIG_SPIRAM_MODE_OCT=y
CONFIG_SPIRAM_SPEED_80M=y
CONFIG_SPIRAM=y
CONFIG_SPIRAM_USE_CAPS_ALLOC=y

# ── Console: USB Serial/JTAG (Type-C, GPIO19/20) ──────────────────────────
CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y
# CONFIG_ESP_CONSOLE_UART_DEFAULT is not set

# ── ESP-Claw Board Manager device support flags ───────────────────────────
CONFIG_ESP_BOARD_DEV_DISPLAY_LCD_SUPPORT=y
CONFIG_ESP_BOARD_DEV_LCD_TOUCH_I2C_SUPPORT=y
CONFIG_ESP_BOARD_DEV_AUDIO_CODEC_SUPPORT=y

# ── LCD framebuffer: double-buffer in PSRAM for smooth rendering ─────────
CONFIG_LCD_PANEL_IO_FORMAT_BUF_SIZE=32768

# ── SPI / QSPI ──────────────────────────────────────────────────────────
CONFIG_SPI_MASTER_IN_IRAM=y

# ── I2S ──────────────────────────────────────────────────────────────────
CONFIG_I2S_ENABLE_DEBUG_LOG=n

# ── Partition table ────────────────────────────────────────────────────
CONFIG_PARTITION_TABLE_CUSTOM=y
CONFIG_PARTITION_TABLE_CUSTOM_FILENAME="partitions_16MB.csv"
```

## Crash encountered and fixed during migration

First successful build, first flash: boot crash-looped with a `StoreProhibited`
panic inside `memcpy`, preceded by repeated:

```
E (...) anim: gfx_anim_prepare_frame(481): prepare frame[N]: frame payload size is invalid
E (...) anim: draw animation: frame[N] header is invalid
E (...) eaf_dec: Invalid bit depth: 255
E (...) eaf_dec: Unknown encoding type: FF
```

This happened AFTER display/touch/audio/button/board-manager init all
succeeded cleanly — confirmed the board port itself was correct. Root cause:
the built-in emote/animation mmap assets are incompatible with this board's
466×466 AMOLED display (likely authored for a different reference display
resolution/format), and the decoder corrupts memory badly enough to crash
inside `memcpy` when fed bad frame data.

Fix applied: `CONFIG_APP_CLAW_ENABLE_EMOTE=n` in sdkconfig. Confirmed clean,
stable boot afterward — full capability registration (73 caps), WiFi
provisioning AP, event router, scheduler, console REPL all came up correctly.

Real fix (not yet done): build/source display-appropriate emote animation
assets for 466×466 AMOLED before re-enabling.

## Result

Migration confirmed successful. Board boots clean on the new repo's standard
`boards/` convention with zero CMake patches, zero manual post-regen steps,
and only one genuine YAML fix (the co5300 dependency) plus one Kconfig
disable (emote, pending asset work). All hardware subsystems verified
working: display, touch, audio (DAC+ADC, correct I2S pin config preserved),
boot button, FATFS, WiFi.
